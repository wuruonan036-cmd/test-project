第 04 课 · Week 1

数据库与 AI 产品数据结构

理解 AI 产品相对普通应用增加的数据对象，以及它们在请求链路中的位置。

数据模型日志评测样本

课程目标

理解 AI 产品相对普通应用增加的数据对象，以及它们在请求链路中的位置。

1. 本课问题域？

当前阶段要先建立一个关键认知：

AI 产品并非只存聊天记录。

普通 App 的数据库主要存用户、订单、内容、设置、日志。 AI App 除了这些，还要存：

text
用户状态
对话历史
消息内容
长期记忆
知识库索引
文件与图片
工具调用结果
模型调用日志
安全检查记录
评测样本

如果不理解数据结构，就很难判断后续开发讨论中的以下内容：

text
用户表怎么设计？
记忆表怎么设计？
对话历史放哪里？
RAG 文档放哪里？
模型调用日志要不要存？
为什么要有 eval dataset？

2. 先从普通 App 数据库理解

数据库可以先理解成：

产品长期记东西的地方。

但它并非一个大号 Excel。 数据库里的数据通常按“对象”组织。

例如一个普通 App 至少会有：

text
User 用户
Post 内容
Comment 评论
Order 订单
Payment 支付
Notification 通知
Log 日志

每一种对象通常会对应一张表。

简单理解：

text
用户表：记录用户是谁
内容表：记录用户发了什么
订单表：记录用户买了什么
日志表：记录系统发生过什么

3. AI App 的数据对象为什么更多？

因为 AI App 多了几个普通 App 没有的东西：

AI 特有对象为什么需要
Conversation 会话一段连续对话的容器
Message 消息用户和 AI 的每一轮发言
Memory 记忆从历史中提取出的长期有用信息
Knowledge Chunk 知识片段RAG 检索用的外部知识
Embedding 向量让系统能做语义检索
Tool Call 工具调用记录模型调用过什么工具
Model Run 模型运行记录一次模型调用的输入、输出、成本、耗时
Guardrail Result 安全检查结果记录输入/输出有没有触发风险
Eval Case 评测样本把失败案例沉淀成测试集

这就是 AI App 数据结构和普通 App 最大的区别。

4. 学习者需要先掌握的 10 个核心数据对象

4.1 User 用户

用户是谁。

可能包含：

text
id
手机号 / 邮箱 / 第三方登录 id
昵称
创建时间
当前阶段
偏好设置
权限状态

在学习者的理解里，User 是所有数据的根。

text
一个用户
→ 有很多会话
→ 有很多消息
→ 有很多记忆
→ 有很多记录
→ 有很多文件

4.2 Session / Conversation 会话

一次对话或一段任务的容器。

例如：

text
今天的一次陪伴对话
一次检查报告解释
一次问医生清单生成
一次夜间紧急咨询

Conversation 并非消息本身，核心是消息的上层容器。

text
Conversation
├─ Message 1：用户问
├─ Message 2：AI 答
├─ Message 3：用户追问
└─ Message 4：AI 继续答

4.3 Message 消息

用户和 AI 的每一条发言。

可能包含：

text
id
conversation_id
user_id
role: user / assistant / system / tool
content
created_at
metadata

role 很关键：

role含义
user用户说的话
assistantAI 回复
system系统指令或隐藏规则
tool工具调用返回结果

需要知道：模型调用时，后端经常会把一组 messages 传给模型。

4.4 User State 用户状态

用户当前处于什么状态。

例如：

text
当前阶段
当前任务
最近一次重要事件
是否有未完成提醒
是否存在风险标记
最近是否在处理某个问题

User State 和 Memory 不一样。

概念解释
User State当前状态，偏实时
Memory长期有用信息，偏长期
Message原始对话记录
Profile用户基础资料

4.5 Memory 记忆

Memory 不同于普通聊天记录，核心是系统从历史信息中抽取出的长期状态。

例如：

text
用户喜欢直接一点的表达
用户不希望频繁收到提醒
用户上次产检后比较焦虑
用户经常担心某类检查指标
用户希望家人版内容更简洁

Memory 通常并非所有内容都写入。 需要有策略：

text
什么值得记？
谁来判断是否写入？
写入后什么时候读取？
用户能不能删除？
删除后还能不能被模型看到？

这就是后面 Memory 课程会重点讲的。

4.6 Record / Card 业务记录

AI 产品里经常不只是聊天，还要把聊天结果沉淀成结构化记录。

例如：

text
检查解释记录
问医生清单
阶段总结
家庭分享卡
提醒事项
回访事项
资料识别结果

这些并非 Message，核心是业务对象。

区别：

类型作用
Message对话本身
Record / Card对话后沉淀出来的结构化结果
Memory从历史中提炼出的长期有用状态
Log系统运行记录

4.7 File / Asset 文件

用户上传的图片、PDF、报告、语音等。

可能包含：

text
文件 id
文件类型
文件地址
上传用户
上传时间
识别结果
关联的会话
关联的业务记录

注意：文件本身一般不直接存在数据库表里，核心是存在对象存储里。 数据库里通常存的是文件地址和元数据。

简单理解：

text
数据库：存文件信息
对象存储：存真实文件

4.8 Knowledge Chunk 知识片段

RAG 里用的知识通常会被切成小块。

例如一篇文档：

text
孕期饮食安全文档

会被切成：

text
chunk 1：关于咖啡因
chunk 2：关于生食
chunk 3：关于叶酸
chunk 4：关于高汞鱼类

每个 chunk 都可能有：

text
chunk_id
source_id
title
content
metadata
embedding
created_at

这里的 embedding 是后面 RAG 课会讲的向量。

4.9 Model Run / AI Call Log 模型调用日志

每一次模型调用都应该可追踪。

至少要知道：

text
用了哪个模型？
输入了什么类型的上下文？
输出是什么？
耗时多久？
花了多少钱？
有没有报错？
有没有调用工具？
有没有触发安全检查？

这类日志对上线后非常关键。

如果没有 Model Run 记录，后续无法回答：

text
为什么这次 AI 答错了？
它当时看了哪些上下文？
是否模型问题？
是否 Prompt 问题？
是否 RAG 检索错了？
是否 Memory 注入错了？

4.10 Eval Case 评测样本

评测样本是 AI 产品从“靠感觉优化”走向“工程化优化”的基础。

例如一次失败回复：

text
用户问题：我今天胎动少了，怎么办？
AI 错误回答：不用担心，休息一下就好。

这类失败案例不能只靠人记住，应该沉淀成 Eval Case：

text
输入问题
期望回答原则
风险等级
错误类型
评分规则
版本信息

以后每次改 Prompt、改模型、改 Harness，都要跑一遍这些测试。

5. 最小 AI App 数据结构总表

暂时无需记忆字段，先记住对象。

数据对象属于哪一层作用
User业务层用户是谁
Profile业务层用户基础资料
Conversation对话层一段会话
Message对话层每一轮消息
User State状态层当前状态
Memory记忆层长期有用信息
Record / Card业务沉淀层AI 输出后的结构化结果
File / Asset文件层图片、报告、语音等
Knowledge Source知识层原始知识文档
Knowledge ChunkRAG 层可检索知识片段
EmbeddingRAG 层语义检索用向量
Tool Call工具层工具调用记录
Model Run观测层模型调用日志
Guardrail Result安全层安全检查结果
Eval Case评测层测试样本
Feedback优化层用户反馈和人工标注

6. 用一条真实链路理解这些数据

用户上传一张检查报告，然后问：

“这个结果严重吗？”

系统可能发生：

text
1. User：识别用户是谁
2. File：保存上传的图片/PDF
3. Conversation：创建一次检查解释会话
4. Message：保存用户问题
5. User State：读取当前阶段、最近事件
6. Knowledge Chunk：检索相关医学知识
7. Memory：读取用户长期偏好或历史担忧
8. Model Run：调用模型生成解释
9. Guardrail Result：检查是否越界诊断
10. Record/Card：生成检查解释记录
11. Message：保存 AI 回复
12. Tool Call：如果调用 OCR 或数据库，也要记录
13. Log：保存运行过程
14. Eval Case：如果这次出错，可沉淀为评测样本

这就是为什么 AI 产品的数据结构比普通聊天 App 复杂。

7. 少量代码：看懂数据模型长什么样

下面并非使学习者写代码，只是使学习者看懂“数据库对象”可能怎么表达。

以 Prisma 风格举例：

prisma
model User {
  id        String   @id
  name      String?
  createdAt DateTime @default(now())
  messages  Message[]
  memories  Memory[]
}
model Message {
  id             String   @id
  userId         String
  conversationId String
  role           String
  content        String
  createdAt      DateTime @default(now())
}
model Memory {
  id        String   @id
  userId    String
  type      String
  content   String
  createdAt DateTime @default(now())
}

只需看懂：

text
User 表示用户
Message 表示消息
Memory 表示记忆
userId 表示这些东西属于哪个用户

不要陷入语法细节。

8. 实战判断：哪些数据一开始必须有？

对于一个 AI App MVP，不要一开始把所有表都做满。

优先级可以这样看：

P0 必须有

text
User
Conversation
Message
Model Run
基本 User State
基础 Record/Card

P1 应该很快有

text
Memory
File / Asset
Tool Call
Guardrail Result
Feedback

P2 后续完善

text
Knowledge Chunk
Embedding
Eval Case
复杂版本管理
精细权限系统

但对于高风险 AI 应用，Model Run、Guardrail Result、Eval Case 的重要性要提前考虑，不能等到上线后才补。
