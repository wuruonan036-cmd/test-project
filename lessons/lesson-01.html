AI App 和普通 App 的工程差异

建立 AI 应用工程的总入口，区分普通软件系统与 AI 系统在后端链路上的关键差异。

总图请求链路Harness 起点

课程目标

建立 AI 应用工程的总入口，区分普通软件系统与 AI 系统在后端链路上的关键差异。

1. 知识树定位

本课在学习者的知识结构图里属于最上层的总入口：

text
AI 应用工程
├─ 基础开发层
├─ 应用后端层
├─ 模型交互层
├─ 上下文 / 知识 / 记忆层
├─ Agent / Harness 控制层
├─ 评测与观测层
└─ 生产化层

这一课只解决一个问题：

AI App 是一套把概率性模型能力纳入确定性软件系统的工程结构，不能简化为“前端 + 大模型 API”。

2. 基础解释：普通 App 怎么工作？

普通 App 可以先理解成一个“确定性机器”。

用户点按钮，系统按预设逻辑执行。

例如外卖 App：

text
用户点“下单”
→ 前端发请求
→ 后端检查购物车
→ 后端计算价格
→ 后端创建订单
→ 数据库保存订单
→ 返回下单成功

这里大部分逻辑是确定的：

text
同样的输入
→ 同样的规则
→ 大体同样的结果

这就是普通软件工程的基本特征：确定性。

3. AI App 多了什么？

AI App 引入了能力强但结果具有概率性的模型层：

text
LLM / 大语言模型

模型的特点是：

text
能理解自然语言
能生成答案
能总结
能推理
能调用工具
能处理复杂上下文
但输出并非 100% 确定

AI App 的核心工程问题包括：

text
怎么让一个概率性模型，稳定地服务一个真实产品？

这就是 AI 应用工程的核心问题。

4. 普通 App 请求链路

普通 App 请求链路可以简化为：

text
用户
→ 前端 UI
→ API
→ 后端业务逻辑
→ 数据库
→ 返回结果
→ 前端展示

可以画成：

mermaid
flowchart LR
  A[用户] --> B[前端 UI]
  B --> C[API 请求]
  C --> D[后端服务]
  D --> E[数据库]
  E --> D
  D --> F[返回结果]
  F --> B

用学习者的语言理解

text
前端负责“用户看到和操作什么”
后端负责“真正做事和管规则”
数据库负责“长期存东西”
API 负责“前端和后端怎么说话”

5. AI App 请求链路

AI App 多了模型和控制系统。

text
用户
→ 前端 UI
→ API
→ 后端服务
→ Harness 判断这次请求
→ 读取用户状态 / 历史 / 记忆 / 知识 / 工具
→ 组装上下文
→ 调用模型
→ 安全检查
→ 返回结果
→ 写日志 / 写记忆 / 写评测样本

可以画成：

mermaid
flowchart LR
  A[用户输入] --> B[前端 UI]
  B --> C[API 请求]
  C --> D[后端服务]
  D --> E[Harness 控制层]
  E --> F[用户状态]
  E --> G[Memory]
  E --> H[RAG / Knowledge]
  E --> I[Tools]
  E --> J[LLM]
  J --> K[Guardrails]
  K --> L[返回前端]
  E --> M[Logs / Traces / Evals]

6. 为什么需要 Harness？

没有 Harness 的 AI App：

text
用户输入
→ 直接塞给模型
→ 模型自由回答

问题是：

text
模型不知道用户是谁
模型不知道产品规则
模型不知道该不该查知识库
模型不知道该不该读记忆
模型不知道能不能调用工具
模型不知道什么场景有风险
模型输出也没有稳定评测

所以真实产品里需要 Harness。

Harness 的一句话定义

Harness 是 AI App 的运行控制层，负责把模型、上下文、知识、记忆、工具、安全、日志组织成一次可控执行。

它不属于模型、单个 Prompt 或某个框架，而应是一套运行控制机制。

7. AI App 比普通 App 多出的核心模块

模块作用0 基础理解
LLM API调用模型将 模型 作为可调用能力
Prompt告诉模型这次怎么做任务说明书
Context告诉模型这次应该看什么信息临时资料包
RAG检索外部知识先查资料，再回答
Memory使用长期用户状态记住对未来有用的信息
Tool Calling调用工具 / API / 数据库让模型不仅会说，还能触发动作
Guardrails安全边界输入、工具、输出都要检查
Evals评测判断模型输出是否合格
Observability可观测性复盘这次为什么这样答
Harness运行控制层总调度员

8. 少量代码：只看结构，不要求会写

下面的代码用于帮助学习者看懂模型调用的基本形态，不要求掌握编写。

ts
app.post("/api/chat", async (req, res) => {
  const userMessage = req.body.message
  const context = await buildContext(userMessage)
  const modelResult = await callLLM({
    prompt: "你是一个 AI 助手",
    userMessage,
    context
  })
  await saveLog({
    userMessage,
    modelResult
  })
  res.json({
    answer: modelResult.text
  })
})

只需看懂这几件事：

text
/api/chat        = 前端调用的接口
userMessage      = 用户输入
buildContext     = 组装上下文
callLLM          = 调模型
saveLog          = 写日志
res.json         = 返回给前端

9. 实战判断

后续看到 AI 产品后端方案，先问 8 个问题：

text
1. 用户请求进来后，谁判断任务类型？
2. 模型调用前，谁组装上下文？
3. 用户历史、记忆、知识库分别在哪里读？
4. 哪些场景调工具，哪些场景不调？
5. 哪些场景必须加安全检查？
6. 模型输出失败怎么办？
7. 每次模型调用有没有日志和 trace？
8. 后续怎么评测和回归？

如果这些问题答不上来，这个方案大概率只是“套了个模型 API”。
