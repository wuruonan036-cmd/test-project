Model Selection / Model Routing：按任务选择合适模型

围绕质量、成本、延迟、上下文、多模态、工具稳定性和安全性设计模型路由。

模型路由成本延迟

课程目标

围绕质量、成本、延迟、上下文、多模态、工具稳定性和安全性设计模型路由。

1. 知识树定位

这一课位于：

text
LLM API
→ Prompt / Context / RAG / Memory / Tool
→ Workflow / Agent / Harness
→ Model Selection / Model Routing
→ Cost / Latency / Evals

模型路由是 Harness 的一个关键子能力。

Harness 要决定：

text
这次任务应该用哪个模型？
是否需要推理模型？
是否需要多模态模型？
是否需要便宜模型？
是否需要低延迟模型？
失败时换哪个模型？

2. 核心结论

模型选型不属于本节重点：

text
哪个模型最强，就全部用哪个。

核心是：

text
不同任务，用不同模型。

这叫 Model Routing。

3. 为什么不能一个模型包打天下？

因为模型选择至少要平衡 6 个维度：

text
质量
成本
延迟
上下文长度
多模态能力
工具调用稳定性
安全与可控性

最强模型通常：

text
更贵
更慢
更适合复杂任务
不一定适合所有高频小任务

轻量模型通常：

text
更便宜
更快
适合分类、摘要、标题、简单结构化任务
但不适合复杂推理和高风险判断

所以真实系统会做模型分工。

4. 模型能力维度

4.1 质量 Quality

回答是否准确、自然、稳定。

适合关注：

text
复杂解释
长文本总结
高质量陪伴回复
结构化生成

4.2 成本 Cost

每次调用要花多少钱。

高频任务尤其要控制成本：

text
任务分类
标题生成
轻量摘要
记忆候选提取
日志标签

4.3 延迟 Latency

用户等多久。

对话产品尤其敏感：

text
用户发一句话
如果 8 秒没反应
体验就会明显下降

低延迟任务应优先用更快模型，或者先流式返回。

4.4 上下文长度 Context Window

有些任务需要读长内容：

text
长对话总结
长报告解释
多份检查记录对比
用户历史记录回看

这类任务要考虑上下文长度和上下文压缩。

4.5 多模态 Multimodal

涉及：

text
图片
检查单
B 超截图
语音
PDF
表格

需要支持图像、语音或文件处理的模型或工具链。

4.6 工具调用稳定性 Tool Calling Stability

有些模型更适合严格结构化输出和工具调用。

如果任务需要：

text
返回 JSON
调用工具
生成函数参数
严格遵守 schema

模型的工具调用稳定性比“语言好不好听”更重要。

4.7 安全与可控性 Safety / Reliability

高风险任务需要更保守：

text
医疗边界
法律边界
心理安全
儿童安全
隐私

并非“说得聪明”就够，还要稳定遵守边界。

5. 典型模型路由表

任务适合模型类型原因
任务分类轻量模型快、便宜、结构化
标题 / 标签生成轻量模型高频低风险
普通聊天中等模型平衡质量、成本、速度
高质量陪伴回复高质量语言模型语气和细腻度重要
复杂问题整理推理模型 / 高质量模型需要多步分析
检查报告解释高质量模型 + RAG准确性与安全边界重要
图片检查单识别多模态模型 / OCR 工具需要图像理解
记忆候选提取轻量或中等模型结构化抽取
记忆冲突判断推理模型需要判断上下文和优先级
输出安全检查轻量模型 + 规则 / 专用分类器高频、规则清晰
深度研究推理模型 + 工具多步骤规划与综合

6. Routing Policy：模型路由策略

不要只写：

text
默认用 GPT-5.5

要写成策略：

text
if task_type == "classification":
    use small_fast_model
if task_type == "check_explanation":
    use high_quality_model + rag
if task_type == "image_report":
    use multimodal_model + ocr_tool
if task_type == "high_risk":
    use conservative_model + guardrails + human_review
if latency_sensitive:
    use faster_model or stream first
if model_error:
    fallback to backup_model

7. 真实系统链路：用户上传一张检查单

模型路由并非只发生一次。

text
用户上传图片
→ OCR / 多模态模型识别文字
→ 轻量模型提取指标
→ RAG 检索指标解释
→ 高质量模型生成解释
→ 安全检查模型判断是否越界
→ 轻量模型生成标题和记录摘要
→ 写入数据库和日志

这就是多模型协作。

8. 少量代码片段：只看结构

ts
function selectModel(task) {
  if (task.type === "classification") {
    return "small-fast-model"
  }
  if (task.type === "image_report") {
    return "multimodal-model"
  }
  if (task.type === "complex_reasoning") {
    return "reasoning-model"
  }
  if (task.type === "safety_check") {
    return "safety-classifier"
  }
  return "general-chat-model"
}

只需理解：

text
模型选择可以被代码策略控制
并非所有任务都调用同一个模型

9. Fallback Model：失败降级

模型调用可能失败：

text
超时
限流
成本太高
返回格式错误
工具调用失败
质量不达标

系统要有 fallback：

text
主模型失败 → 备用模型
结构化输出失败 → 重新生成
RAG 失败 → 明确提示信息不足
安全检查失败 → 输出保守回复
工具失败 → 告知用户稍后重试

10. Model Routing 和 Evals 的关系

模型路由不能只靠感觉。

学习者需要用评测验证：

text
同一批样本
模型 A 表现如何
模型 B 表现如何
模型 C 成本是多少
延迟是多少
错误类型是什么

最后做判断：

text
这个任务用哪个模型最划算？
哪个模型更稳定？
哪个模型适合高风险场景？
哪个模型可以作为 fallback？

所以模型路由和 Evals 强绑定。

11. 常见误区

误区正确理解
最强模型最好最适合任务的模型最好
便宜模型质量一定差很多分类、摘要、标签任务轻量模型足够
推理模型适合所有任务推理模型可能更慢、更贵，不适合高频简单任务
模型路由上线后再做早期就要设计任务类型和路由策略
Fallback 可有可无没 fallback，系统稳定性很差
模型选型只看效果还要看成本、延迟、格式稳定性、工具调用能力

12. 本课实战判断

后续评审模型方案时，必须问：

text

2. 这个任务是否高频？
3. 用户是否能等待？
4. 是否需要多模态？
5. 是否需要严格 JSON？
6. 是否涉及风险边界？
7. 是否有备用模型？
8. 是否有评测样本验证？
9. 是否有成本估算？
10. 是否记录每次模型调用？

阶段复盘

这三课可以合成一个核心判断：

text
Workflow / Agent 决定“怎么执行”
Harness 决定“怎么控制”
Model Routing 决定“用哪个模型执行”

三者关系：

text
用户输入
→ Harness 识别任务
→ 决定走 Workflow / Agent / Hybrid
→ 组装 Context
→ 读取 RAG / Memory / Tool
→ 根据任务选择模型
→ 输出前安全检查
→ 写日志
→ 进入 Evals

需要形成的最终判断：

AI 应用工程不能简化为“前端 + 模型 API”，核心是一个由任务识别、流程编排、上下文管理、模型路由、工具权限、安全检查、日志评测共同组成的运行系统。
