主流框架与实现参考：框架作为工程实现方式

把 Vercel AI SDK、LlamaIndex、LangGraph、OpenAI Agents SDK、Pydantic AI、Mem0 等放回底层知识结构。

框架参考选型收官复盘

课程目标

把 Vercel AI SDK、LlamaIndex、LangGraph、OpenAI Agents SDK、Pydantic AI、Mem0 等放回底层知识结构。

1. 知识树定位

这一课不做“框架排行榜”。

它解决的是：

text
底层知识点
→ 对应有哪些实现工具
→ 这些工具适合解决什么问题
→ 如何判断是否需要它

需要形成的基本认知：

框架是工程能力的封装，不等同于底层知识本体。

错误学习方式：

text
今天学 LangGraph
明天学 CrewAI
后天学 Mem0
再看 Vercel AI SDK
最后脑子里全是名字

正确学习方式：

text
先理解：
Workflow 是什么
Agent 是什么
Memory 是什么
Tool Calling 是什么
RAG 是什么
Evals 是什么
再看：
哪个框架解决其中哪个问题

3. 不同工具在知识结构里的位置

3.1 Vercel AI SDK：前端 AI 体验 + TypeScript AI 调用

适合理解：

text

初期无需深入学习它，但如果学习者的前端是 React / Next.js，它会非常相关。

需要知道它解决的是：

text
怎么让 AI 能自然进入 Web App 的前端体验

不属于本节重点：

text
完整 AI 后端架构

text

学习重点应放在以下结构，而非具体 API 用法：

text

3.3 LangGraph：Workflow / Agent / State / Durable Execution

适合理解：

text
State
Node
Edge
Graph
Checkpoint

学习重点应放在背后的工程结构，具体语法可后置。

text
用图和状态机管理复杂 AI 工作流

这比“多个 Agent 互相聊天”更重要。

3.4 OpenAI Agents SDK：Agent、Tool、Guardrails、Tracing 的整体参考

OpenAI Agents SDK 的价值在于用于观察一个官方 Agent 框架如何组织：

text
Agent
Tool
Handoff
Guardrails
Tracing
Human review

它适合作为理解 Harness 的参考。

需要关注：

text
一次 agent run 中发生了什么？
工具如何调用？
guardrails 放在哪里？
trace 记录了什么？

3.5 Pydantic AI：Python 侧 production-grade Agent / Workflow 参考

Pydantic AI 官方定位是用于构建 production-grade Generative AI applications and workflows 的 Python agent framework。

它对学习者有两个学习价值：

text
1. 理解 Python AI 后端如何组织 agent / tool / structured output
2. 理解类型校验、结构化输出、评测、可观测性如何进入 AI 工程

如果未来走 Python AI 服务路线，它值得关注。

3.6 Mem0 / Letta / Zep：Memory 参考

这类工具的首要价值不在于立即接入。

它们更适合理解：

text
Memory 与聊天记录存在明确边界
记忆需要写入策略
记忆需要检索策略
记忆需要更新和删除
记忆可能需要图谱结构
记忆需要安全和评测

学习顺序应该是：

text
先学 Memory 类型与原则
再看 Mem0 / Letta / Zep 各自怎么实现

3.7 Braintrust / Phoenix / LangSmith / OpenAI Evals：评测观测参考

这些工具用于回答：

text
模型为什么这么答？
这次用了什么上下文？
工具调用是否成功？
新版本是否比旧版本更好？
线上失败案例怎么转成测试集？

这类工具在 Demo 阶段优先级较低，但对上线后的持续改进非常关键。

4. 框架选择的第一性原理

框架选型应围绕 7 个问题展开：

text
1. 它解决的是我现在的问题吗？
2. 它是核心链路还是辅助链路？
3. 它会不会增加过多复杂度？
4. 团队能不能维护？
5. 它是否有清晰文档和活跃社区？
6. 它是否容易替换？
7. 它是否让系统更可控，还是更不可控？

5. 常见错误

错误正确判断
看到框架火就接先判断底层问题是否真的存在
将 LangGraph 作为万能 Agent 工具LangGraph 更核心的是状态、图、可恢复执行
一上来就多智能体先 Workflow，再 Agent，再 Multi-agent
Memory 直接接工具先定义记忆策略，再选实现
前端 AI SDK 代替后端架构前端 SDK 解决体验，不解决全部后端控制
没有 eval 就换模型先建立评测集，再比较模型
所有东西都用一个框架真实系统通常是多个轻量模块组合

2. 当前阶段应该具备的 8 个判断

判断 1：AI App 不能简化为“前端 + 模型 API”

它至少需要：

text
用户系统
后端接口
数据库
模型调用
上下文组装
知识库
记忆系统
工具调用
安全控制
日志评测
部署运维

判断 2：Prompt 只是 AI 工程的一部分

Prompt 只是其中一层。

真正稳定的 AI 系统需要：

text
Prompt
+ Context
+ Structured Output
+ RAG
+ Memory
+ Tool
+ Guardrails
+ Evals
+ Observability

判断 3：Context 比 Prompt 更接近系统能力

Prompt 是“怎么做”。

Context 是：

text
这一次让模型看到什么
不让模型看到什么
哪些信息更重要
哪些历史应该压缩
哪些记忆应该注入
哪些知识应该检索

判断 4：RAG、Memory、Database 存在明确工程边界

概念解决什么
Database存确定性业务数据
RAG查外部知识
Memory维护用户长期状态
Context本次模型调用看到的信息
Tool执行外部动作

判断 5：Workflow 优先，Agent 后置

能用固定流程解决的，不要一上来 Agent。

text
高风险 / 标准化任务 → Workflow
开放探索 / 多步骤动态任务 → Agent
真实产品 → Hybrid

判断 6：Harness 是 AI 产品后端的控制中枢

Harness 要决定：

text
任务类型
风险等级
上下文
模型
工具
记忆
安全
降级
日志
评测

判断 7：Evals 和 Observability 是上线后的生命线

没有 Evals：

text
不知道新版本是否变好
不知道模型切换是否有效
不知道 Prompt 修改是否出问题

没有 Observability：

text
不知道一次错误是模型问题、上下文问题、RAG 问题、记忆问题还是工具问题

判断 8：框架只是实现方式，并非知识本体

学习者应当先问：

text
我到底要解决什么底层问题？

再问：

text
哪个框架适合解决？

不要反过来。
