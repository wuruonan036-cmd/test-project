第 06 课 · Week 2

LLM API 基础：模型如何被产品调用

理解模型调用的输入、输出、参数和流式响应，为 Prompt 与 Context 学习打底。

LLM APIMessagesTokens

课程目标

理解模型调用的输入、输出、参数和流式响应，为 Prompt 与 Context 学习打底。

1. 本课问题域？

学习者可能先把大模型理解成：

一个聊天框。

但在产品里，大模型更准确地说是：

一个可以被后端调用的智能能力接口。

产品调用模型的方式，是由后端将输入发送给模型 API，并把模型输出处理成产品流程的一部分。

2. LLM API 是什么？

API 是系统之间沟通的入口。

LLM API 就是：

text
学习者的后端
→ 把用户输入、系统指令、上下文、参数发给模型服务
→ 模型返回文本、结构化数据或工具调用请求
→ 学习者的后端继续处理

可以把 LLM API 想成一个智能外部服务。

普通 API 可能是：

text
查询天气
查询订单
发送短信
上传文件

LLM API 是：

text
理解用户输入
生成回复
总结文本
提取结构化信息
判断任务类型
调用工具
解释图片
生成 JSON

3. 一次模型调用的基本组成

一次 LLM API 调用通常包含：

text
model：用哪个模型
input / messages：给模型什么内容
instructions / system：系统级要求
tools：模型可以调用哪些工具
temperature：输出随机性
max output tokens：最多输出多长
stream：是否流式输出
response format：是否要求结构化输出

先不用记所有参数，先记四个核心：

text
模型是谁
输入是什么
上下文是什么
输出要什么格式

4. Messages 是什么？

在聊天型模型里，输入经常被组织成 messages。

一个 messages 通常长这样：

json
[
  {
    "role": "system",
    "content": "你是一个专业、克制、准确的 AI 助手。"
  },
  {
    "role": "user",
    "content": "帮我解释一下这份报告。"
  },
  {
    "role": "assistant",
    "content": "可以，我先帮助学习者看关键指标。"
  },
  {
    "role": "user",
    "content": "这个指标偏高严重吗？"
  }
]

需要理解 role：

role含义
system系统给模型的规则
user用户输入
assistant模型之前的回复
tool工具调用返回的结果

系统传给模型的是经过整理的一组上下文，而非最后一句用户输入。

5. System / User / Assistant 的区别

5.1 System

系统级规则。

例如：

text
你不能替代医生诊断。
回答必须简洁。
遇到危险信号要建议用户及时就医。
输出必须符合 JSON Schema。

System 通常由产品和工程团队控制，用户看不到。

5.2 User

用户输入。

例如：

text
我有点担心这个指标。
帮我总结这个报告。
这段话怎么跟家人说？

User 是用户直接说的话。

5.3 Assistant

模型之前生成的内容。

它用于保持上下文连续。

例如：

text
上一轮 AI 已经解释过一个指标
这一轮用户追问“那我需要注意什么？”
模型需要知道“那”指什么

所以历史 assistant 消息有时要带进去，有时要裁剪。

这就进入后面的 Context Engineering。

6. Token 是什么？

Token 可以先理解成模型处理文本的基本单位。

它既不严格等于字，也不严格等于词。

当前阶段只需要知道：

text
输入越长，token 越多
输出越长，token 越多
token 越多，成本越高
token 越多，速度可能越慢
模型上下文窗口有上限

所以 AI 产品不能把所有历史对话都塞给模型。 这就是为什么需要 Context Engineering。

7. Temperature 是什么？

Temperature 可以理解为输出随机性。

Temperature效果
低更稳定、更保守、更一致
高更发散、更有创意、更不可控

对产品来说：

text
高风险、解释类、结构化任务 → 低 temperature
创意写作、头脑风暴 → 可以稍高

无需记忆具体数字，先掌握判断逻辑：

任务越需要稳定，随机性越低。

8. Streaming 是什么？

Streaming 是流式输出。

Streaming 的特点是边生成边返回，而并非等待完整结果后一次性返回。

用户体验上就是：

text
AI 一边思考一边逐步显示内容

为什么重要？

text
降低等待感
增强对话流畅度
适合聊天和陪伴场景
不一定适合所有后台任务

例如报告生成可以等一会儿，但聊天页最好流式输出。

9. Multimodal 是什么？

Multimodal 多模态，指模型能处理不止文本。

包括：

text
文本
图片
语音
PDF / 文档
视频帧

在 AI 产品里，多模态意味着用户可以：

text
拍照上传报告
发语音
上传截图
让 AI 看图解释

但注意：

text
多模态识别结果不等于专业诊断
OCR 识别可能错
图片理解可能漏
高风险场景必须有边界

10. 少量代码：模型调用大概长什么样？

下面的代码用于阅读结构，不要求编写。

ts
const response = await client.responses.create({
  model: "gpt-5.5",
  input: [
    {
      role: "system",
      content: "你是一个专业、克制、准确的 AI 助手。"
    },
    {
      role: "user",
      content: "帮我解释一下这份报告。"
    }
  ]
})

只需看懂：

text
model：使用哪个模型
input：传给模型什么内容
role: system：系统规则
role: user：用户问题
response：模型返回结果

11. LLM API 在真实系统中的位置

一次聊天请求可能是：

text
1. 前端收集用户输入
2. 前端发请求到后端 /api/chat
3. 后端读取用户信息
4. 后端组装 messages
5. 后端选择模型
6. 后端调用 LLM API
7. 模型返回回复
8. 后端做安全检查
9. 后端保存 Message 和 Model Run
10. 后端把结果返回前端

LLM API 是产品链路中的一环，不等同于完整产品。

12. LLM API 的三种常见输出

12.1 文本输出

最常见：

text
用户问一句
AI 回一段话

适合：

text
普通对话
解释
总结
安抚
建议

12.2 结构化输出

返回 JSON。

适合：

text
任务分类
风险等级
字段提取
生成卡片
创建提醒
生成数据库记录

例如：

json
{
  "task_type": "medical_question",
  "risk_level": "medium",
  "should_call_tool": false,
  "reply_style": "concise"
}

12.3 工具调用请求

模型不直接回答，核心是说：

text
我需要调用某个工具。

例如：

json
{
  "tool_name": "search_knowledge_base",
  "arguments": {
    "query": "孕期胎动减少"
  }
}

然后后端决定是否允许调用。

13. 实战判断：什么时候不能直接调用模型？

以下场景不建议直接：

text
高风险医疗
法律/财务等高风险建议
需要调用数据库
需要创建提醒
需要写入记忆
需要生成结构化记录
需要使用外部知识
需要可追踪和回放

这些都应该通过 Harness 管控：

text
任务识别
上下文组装
模型路由
工具权限
安全检查
日志记录
失败降级

14. LLM API 和后面课程的关系

text
LLM API
├─ Prompt：怎么指挥模型
├─ Structured Output：怎么让模型输出机器可用结果
├─ Context：这次给模型看什么
├─ RAG：从知识库拿什么给模型看
├─ Memory：从用户历史拿什么给模型看
├─ Tool Calling：模型如何请求外部动作
├─ Harness：谁来决定以上流程
├─ Guardrails：谁来检查风险
└─ Evals：怎么判断效果好不好

所以第 06 课是后面所有 AI 工程内容的入口。
