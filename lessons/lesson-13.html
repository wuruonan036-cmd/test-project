第 13 课 · Week 3

Workflow vs Agent：AI 系统编排方式的边界

掌握常见工作流模式、Agent 的适用边界和多 Agent 的成本风险。

WorkflowAgent编排

课程目标

掌握常见工作流模式、Agent 的适用边界和多 Agent 的成本风险。

1. 知识树定位

在学习者的 AI 应用工程知识树里，这一课位于：

text
基础开发
→ 后端基础
→ LLM API
→ Prompt / Structured Output / Context
→ RAG / Memory / Tool
→ Workflow / Agent
→ Harness
→ Evals / Observability / LLMOps

它连接前面的三个模块：

text
RAG：查外部知识
Memory：处理长期状态
Tool：调用外部能力

并为后面的 Harness 做准备：

text
Harness：决定什么时候走 Workflow，什么时候用 Agent，什么时候降级，什么时候人工介入。

2. 核心结论

本课需要建立的核心判断是：

真实 AI 产品中，并非所有复杂任务都适合 Agent；关键流程通常应优先采用 Workflow。

一句话区分：

text
Workflow = 人提前设计好步骤，模型按步骤参与。
Agent = 模型动态决定下一步该做什么。

更实用的判断：

类型谁决定流程适合什么场景风险
Workflow人 / 代码标准化、高风险、可预测任务灵活性较低
Agent模型开放式、多步骤、不确定任务可控性较弱
Hybrid人设计主流程，模型在局部决策真实产品常见形态需要 Harness 管好边界

3. 为什么不能在所有场景默认使用 Agent？

因为 Agent 的强项也是风险来源。

Agent 的强项：

text
它可以自己判断下一步
它可以调用多个工具
它可以分解任务
它可以根据中间结果继续行动

Agent 的风险：

text
它可能多做
它可能漏做
它可能错误调用工具
它可能走错流程
它可能浪费 token 和成本
它可能在高风险场景越界

所以第一性原理是：

产品越高风险，越需要确定性流程；任务越开放，越需要模型自主性。

比如：

场景推荐
用户上传检查报告，系统解释结果Workflow
用户说“我最近很乱，你帮我整理一下”Hybrid
用户要生成问医生清单Workflow + 模型生成
用户连续多轮倾诉，问题不断变化Agent-like
系统做复杂资料研究和交叉验证Agent / Multi-agent
医疗红旗信号判断Workflow + 规则 + 保守模型

4. 5 种常见 Workflow 模式

Anthropic 的《Building Effective Agents》里总结了几类实用模式。无需记忆名称，但要理解它们解决的问题。

4.1 Prompt Chaining：提示链

本质

把一个复杂任务拆成多个小步骤，每一步输出给下一步。

text
输入
→ 步骤 1：分类
→ 步骤 2：检索
→ 步骤 3：生成
→ 步骤 4：检查
→ 输出

适合

text
任务步骤比较清楚
每一步都能验证
需要控制质量

例子

用户上传检查报告：

text
1. 识别报告类型
2. 提取关键指标
3. 查知识库
4. 生成解释
5. 生成问医生清单
6. 安全检查

这里不需要 Agent 自由发挥。更适合 Workflow。

4.2 Routing：路由

本质

先判断任务类型，再分发到不同处理流程。

text
用户输入
→ 任务分类
→ A 流程 / B 流程 / C 流程

适合

text
用户输入类型很多
不同类型需要不同模型或流程

例子

用户说一句话，系统先判断：

text
情绪陪伴
检查解释
饮食建议
问医生清单
风险信号
资料导入
普通闲聊

然后走不同链路。

4.3 Parallelization：并行处理

本质

多个子任务同时进行，然后合并结果。

text
输入
→ 子任务 A
→ 子任务 B
→ 子任务 C
→ 汇总

适合

text
任务之间互不依赖
需要提高速度
需要多个视角

例子

分析一份检查报告时，可以并行做：

text
指标提取
风险词识别
知识库检索
历史记录匹配

最后合并成一个结果。

4.4 Orchestrator-Workers：调度者-执行者

本质

一个中心模型先拆任务，再分配给多个 worker 完成，最后汇总。

text
Orchestrator：判断任务怎么拆
Worker A：处理子任务 A
Worker B：处理子任务 B
Worker C：处理子任务 C
Orchestrator：汇总

适合

text
任务复杂
子任务数量不确定
需要动态拆解

例子

做一次深度研究报告：

text
一个模型规划研究问题
多个子任务分别查资料、整理竞品、分析用户评论
最后汇总成报告

这更接近 Agentic Workflow。

4.5 Evaluator-Optimizer：评估者-优化者

本质

一个模型生成结果，另一个模型检查并提出改进，循环直到达标。

text
生成
→ 评估
→ 修改
→ 再评估
→ 输出

适合

text
质量要求高
输出可以被标准检查
需要反复优化

例子

生成一份“给医生看的问题清单”：

text
生成初稿
→ 检查是否医学越界
→ 检查是否问题清晰
→ 检查是否遗漏用户关键信息
→ 修订

5. Workflow、Agent、Multi-agent 的边界

5.1 Workflow

核心是：

text
代码控制流程，模型完成局部任务。

例子：

text
检查报告解释流程
资料导出流程
主动回访流程
问医生清单生成流程

5.2 Agent

核心是：

text
模型控制下一步行动。

例子：

text
复杂问题整理
多轮开放式陪伴
研究型任务
多工具综合处理

5.3 Multi-agent

核心是：

text
多个 Agent / 模型角色协作。

但需要警惕：

Multi-agent 的价值在于任务拆解、角色分工、结果校验和可观测性，而并非多个角色聊天。

真实产品里，多智能体不应该作为第一层架构。它是高级能力。

6. 真实系统链路：用户说“我有点不舒服，帮我看看要不要问医生”

不要直接进入一个万能 Agent。

更合理的链路是：

text
用户输入
→ 任务分类：症状 / 情绪 / 医疗风险可能
→ 风险初筛：是否有红旗信号
→ 读取用户状态：孕周、历史检查、既往风险
→ 走 Workflow：
   1. 提取症状
   2. 匹配风险规则
   3. 检索知识库
   4. 生成建议
   5. 生成问医生清单
→ 输出前 Guardrails
→ 记录日志
→ 必要时创建回访

这里的主流程应是 Workflow。模型只在几个节点发挥作用。

7. 少量代码片段：只看结构

不要纠结语法，只看“流程被代码固定下来”。

ts
async function handleUserMessage(input, userId) {
  const task = await classifyTask(input)
  if (task.type === "risk_signal") {
    return await riskWorkflow(input, userId)
  }
  if (task.type === "check_report") {
    return await checkReportWorkflow(input, userId)
  }
  if (task.type === "open_chat") {
    return await companionAgent(input, userId)
  }
  return await fallbackChat(input, userId)
}

只需理解：

text
系统先分类
再决定走哪个流程
并非所有问题都交给同一个 Agent

8. 常见误区

误区正确理解
Agent 越多越高级可控性比数量重要
Agent 能替代后端流程不能，Agent 只是能力之一
Workflow 太死板高风险任务恰恰需要 Workflow
Multi-agent 适合所有复杂任务很多复杂任务用单 Agent + 工具 + Workflow 更稳
先选框架再设计流程先设计流程，再选实现方式

9. 本课实战判断

后续评审 AI 架构时，先问 5 个问题：

text
1. 这个任务流程是否可预测？
2. 错误代价高不高？
3. 是否需要模型动态拆解步骤？
4. 中间结果能不能被验证？
5. 失败时有没有降级路径？

判断规则：

text
流程可预测 + 错误代价高 → Workflow
流程不确定 + 任务开放 → Agent
需要多个专业子任务 + 可观测性强 → Multi-agent / Orchestrator-workers
