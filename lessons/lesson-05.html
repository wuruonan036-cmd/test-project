2. 普通 App 的最小链路

普通 App 可以先理解成：

text
用户操作
→ 前端页面
→ API 请求
→ 后端服务
→ 数据库
→ 返回结果
→ 前端展示

例如用户点“查看订单”：

text
用户点击订单页
→ 前端请求 /api/orders
→ 后端验证登录
→ 数据库查询订单
→ 返回订单列表
→ 前端展示

它的核心是确定性逻辑：

text
输入比较清楚
逻辑由代码决定
输出相对稳定

3. AI App 的最小链路

AI App 多了模型，所以链路变成：

text
用户输入
→ 前端页面
→ API 请求
→ 后端服务
→ 读取用户状态
→ 组装上下文
→ 调用模型
→ 输出结果
→ 写入消息 / 日志 / 记录
→ 返回前端

但这还只是“裸模型调用”。

真正可上线的 AI App 需要再加：

text
任务识别
风险识别
RAG 检索
Memory 读写
Tool Calling
Guardrails
Tracing
Evals
Fallback

所以完整一点是：

text
用户输入
→ 前端
→ API
→ 后端
→ Harness
   ├─ 任务识别
   ├─ 风险识别
   ├─ 用户状态读取
   ├─ 上下文组装
   ├─ RAG 检索
   ├─ Memory 读取
   ├─ Tool 权限判断
   ├─ 模型路由
   └─ 输出控制
→ LLM
→ Guardrails
→ 返回前端
→ 数据沉淀
→ Logs / Traces / Evals

4. 为什么 AI App 不能只是“前端 + 模型 API”？

因为模型有几个天然问题：

问题影响
输入不稳定用户表达很模糊，系统需要先判断任务
输出不稳定同样问题可能得到不同答案
上下文有限不能把所有历史都塞进去
模型会幻觉需要 RAG、边界和检查
不能天然记住用户需要 Memory 系统
不能随便操作外部系统需要 Tool 权限和校验
难以复盘需要 Logs / Tracing
难以持续优化需要 Evals

AI App 后端需要承担以下控制职责：

用软件工程把模型能力包进一个可控、可观测、可评测、可上线的系统里。

6. 用一条“AI 请求链路”重新串起来

假设用户说：

“帮我解释一下这个检查结果。”

完整链路可以这样理解：

text
1. 前端接收用户输入和文件
2. 前端发请求到 /api/chat 或 /api/report/explain
3. 后端验证用户身份
4. 后端保存文件信息
5. 后端创建 Conversation
6. 后端保存 Message
7. Harness 判断任务类型：检查解释
8. Harness 判断是否涉及高风险
9. 读取 User State：当前阶段、历史记录
10. 检索 Knowledge：相关检查指标知识
11. 读取 Memory：用户偏好、历史担忧
12. 组装 Context Pack
13. 选择模型：解释类任务用更稳定的模型
14. 调用 LLM
15. 输出前做 Guardrails 检查
16. 生成结构化 Record/Card
17. 保存 Message 和 Model Run
18. 返回前端展示
19. 记录 Trace
20. 如果出错，沉淀为 Eval Case

这就是后续所有学习的主线。

7. 当前阶段应该能区分的 8 组概念

7.1 前端 vs 后端

概念作用
前端用户看见和操作的界面
后端处理请求、数据、模型、权限、业务逻辑

7.2 API vs Database

概念作用
API前后端沟通的入口
Database长期存数据的地方

7.3 Message vs Memory

概念作用
Message原始对话内容
Memory从历史中提取出来的长期有用状态

7.4 Record/Card vs Log

概念作用
Record/Card给用户看的结构化业务结果
Log给系统和开发看的运行记录

7.5 RAG vs Database

概念作用
Database存业务数据
RAG检索外部知识给模型使用

7.6 Context vs Prompt

概念作用
Prompt告诉模型怎么做
Context告诉模型这次基于什么信息做

7.7 Workflow vs Agent

概念作用
Workflow人预先设计流程
Agent模型动态决定步骤

7.8 Harness vs Model

概念作用
Model生成、理解、推理
Harness控制模型何时、如何、基于什么、在什么边界下工作

8. 看代码时当前阶段只需要看懂什么？

当前阶段不需要细看语法。

看到一个项目，先找：

text
package.json：项目怎么启动、依赖什么
src/：主要代码在哪里
api/ 或 routes/：后端接口在哪里
components/：前端组件在哪里
lib/ 或 services/：模型调用、数据库调用可能在哪里
schema.prisma 或 migrations/：数据库结构在哪里
.env：环境变量在哪里

第一判断应聚焦于工程入口和模块关系：

text
这个文件大概负责什么？
这个模块在系统链路里处于什么位置？
它和前端/后端/模型/数据库哪个环节有关？
