Guardrails / Safety：AI 系统安全护栏

理解输入、任务、工具、输出和产品动作上的安全控制节点。

安全Guardrails人工确认

课程目标

理解输入、任务、工具、输出和产品动作上的安全控制节点。

1. 这一课在知识树里的位置

当前阶段已经学过：

text
LLM API
→ Prompt
→ Structured Output
→ Context
→ RAG
→ Memory
→ Tool Calling
→ Workflow / Agent
→ Harness
→ Model Routing

接下来要补的是：

text
AI 系统能做事了之后，怎么避免它做错事、乱做事、越界做事？

这就是 Guardrails / Safety。

它属于：

text
Harness 控制层
└─ 安全控制
   ├─ Input Guardrails
   ├─ Output Guardrails
   ├─ Tool Guardrails
   ├─ Policy Check
   ├─ Human Review
   └─ Fallback / Refusal / Safe Completion

2. 先建立一个底层理解

很多人会把 Guardrails 理解成：

text
敏感词过滤

这个理解太窄。

真正的 Guardrails 是：

text
在 AI 系统的关键节点上，对输入、任务、工具、输出、动作进行检查和约束。

也就是：

text
不仅检查用户输入内容
核心是检查：
用户输入能不能处理
这是什么风险等级
模型能不能调用这个工具
工具参数是否合法
模型输出能不能展示
是否需要人工确认
是否需要拒绝或降级

3. Guardrails 放在哪些节点？

最少有 5 个节点。

text
用户输入
→ Input Guard
→ 任务识别 / 风险识别
→ Tool Guard
→ 模型生成
→ Output Guard
→ 产品动作执行前检查
→ 返回用户 / 写入系统

3.1 Input Guardrails

检查用户输入。

它回答：

text
这个输入是否能处理？
是否存在高风险？
是否需要进入特殊流程？
是否需要拒绝？
是否需要转人工或建议专业帮助？

例子：

text
用户输入：我现在剧烈腹痛，还出血了，怎么办？

这类场景需要先识别风险，再决定是否进入常规回复流程。

3.2 Task / Risk Classification

这一步一般属于 Harness。

它回答：

text
这是闲聊？
是知识问答？
是医学风险？
是心理危机？
是文件理解？
是工具任务？

注意：这一步不一定只靠 LLM，可以是：

text
规则 + 分类模型 + LLM 判断 + 关键词 + 用户状态

3.3 Tool Guardrails

检查模型是否可以调用某个工具。

例子：

text
模型想调用 send_family_message 工具

系统必须检查：

text
用户是否授权？
收件人是否合法？
内容是否涉及隐私？
是否需要二次确认？
是否允许自动发送，还是只能生成草稿？

Tool Guardrails 非常重要，因为工具调用会产生真实后果。

3.4 Output Guardrails

检查模型生成的内容能不能展示给用户。

它回答：

text
有没有越界建议？
有没有不确定却装确定？
有没有医疗诊断倾向？
有没有错误承诺？
有没有隐私泄露？
有没有不该强化的表达？

3.5 Action Guardrails

检查模型输出之后的产品动作。

比如：

text
是否写入记忆？
是否生成提醒？
是否创建空间记录？
是否发送给家人？
是否调用外部服务？

模型说“可以写入记忆”不代表系统就一定写。最终应该由代码规则和权限策略决定。

4. Guardrails 和 Harness 的关系

Guardrails 通常由 Harness 调用，不应作为孤立模块理解。

text
Harness 决定流程
Guardrails 检查边界

一次完整请求里，Harness 可能这样工作：

text
1. 接收用户输入
2. 调 Input Guard
3. 做任务分类
4. 加载用户状态
5. 组装 Context
6. 决定模型和工具
7. 调 Tool Guard
8. 调模型
9. 调 Output Guard
10. 决定是否写记录 / 写记忆 / 触发回访
11. 写日志和 trace

所以后续看任何 AI 架构时，要问：

text
它的 Guardrails 是放在 Harness 里的，还是只是在 Prompt 里写了一句“不要乱说”？

只靠 Prompt 约束安全，通常不够。

5. 少量代码：只需看懂结构

下面的代码用于定位工程位置，不要求编写。

ts
async function handleUserMessage(userId: string, message: string) {
  const inputCheck = await runInputGuard(message)
  if (inputCheck.blocked) {
    return inputCheck.safeReply
  }
  const task = await classifyTask(message)
  const context = await buildContext(userId, task)
  const modelOutput = await callModel({
    task,
    context,
    message
  })
  const outputCheck = await runOutputGuard(modelOutput)
  if (!outputCheck.safe) {
    return outputCheck.fallbackReply
  }
  await saveLog({ userId, task, inputCheck, outputCheck })
  return modelOutput
}

只需看懂：

text
runInputGuard = 输入前检查
classifyTask = 任务分类
buildContext = 上下文组装
callModel = 调模型
runOutputGuard = 输出后检查
saveLog = 留痕

6. 常见误区

误区 1：把 Guardrails 写进 Prompt 就够了

不够。Prompt 是软约束，工程系统需要硬约束。

误区 2：只检查输入，不检查工具

工具调用最危险，因为它会产生真实动作。

误区 3：只检查输出文本，不检查产品动作

例如“写入记忆”“发送消息”“创建提醒”这些动作也要检查。

误区 4：所有问题都让模型判断风险

高风险领域不能完全依赖模型自由判断。应该有规则、阈值、分类器、人工确认和 fallback。

7. 学习者需要形成的判断表

问题是否需要 Guardrails为什么
普通闲聊中防止越界、攻击、隐私问题
医疗相关问题高不能替代医生，不能误导
心理危机表达极高需要特殊安全流程
记忆写入高涉及隐私和长期影响
家庭分享高涉及第三方和隐私授权
工具调用高可能产生真实动作
生成摘要标题低-中主要防止误导和泄露
