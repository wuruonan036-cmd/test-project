2. 基础解释：什么是部署？

可以先这样理解：

部署 Deployment = 把本地能跑的代码，放到真实用户能访问的服务器 / 云平台上运行。

一个本地 Demo 通常是：

text
学习者的电脑
→ npm run dev
→ http://localhost:5173
→ 只在本机可见

一个上线服务是：

text
真实用户手机 / 浏览器
→ 访问正式域名
→ 请求进入云服务器
→ 后端执行
→ 数据库保存
→ 模型 API 调用
→ 日志记录
→ 结果返回给用户

所以部署是一组工程交付动作，至少涉及：

text
代码在哪里运行？
数据存在哪里？
API Key 怎么保护？
服务挂了谁知道？
模型超时怎么办？
成本突然升高怎么办？
线上错误怎么回滚？

3. 什么是 LLMOps？

LLMOps 可以理解为：

围绕大模型应用的上线、监控、评测、成本、安全和版本管理。

普通 DevOps 关心：

text
服务能不能跑
数据库是否正常
接口是否报错
服务器是否宕机

LLMOps 还要多关心：

text
模型输出是否变差
Prompt 版本是否稳定
上下文是否拼错
RAG 是否检索错内容
Memory 是否错误注入
Tool 是否被错误调用
Token 成本是否异常
模型延迟是否可接受

也就是说：

text
DevOps 管软件稳定性
LLMOps 管 AI 行为稳定性 + 软件稳定性

4. AI 应用上线前必须理解的 10 个问题

4.1 Environment Variables：环境变量

环境变量就是：

不应该写死在代码里的配置。

例如：

text
OPENAI_API_KEY
DATABASE_URL
REDIS_URL
JWT_SECRET
MODEL_NAME
LOG_LEVEL

错误做法：

ts
const apiKey = "sk-xxxxxxx"

正确方向：

ts
const apiKey = process.env.OPENAI_API_KEY

无需掌握编写细节，但要能判断：

text
API Key 不能写在前端
API Key 不能提交到 GitHub
API Key 应该放在服务端环境变量或密钥管理系统里

OpenAI API 文档也明确强调 API Key 是 secret，不应暴露在客户端代码中，应从环境变量或密钥管理服务中安全加载。

4.2 API Key 管理

AI 产品通常会有很多 Key：

text
OpenAI / Anthropic / Gemini API Key
数据库连接 Key
对象存储 Key
短信服务 Key
OCR 服务 Key
支付服务 Key
日志服务 Key

需要理解一个基本原则：

text
前端不能直接拿核心 API Key 调模型

否则风险是：

text
Key 被偷
费用被刷爆
用户绕过权限直接调用模型
数据泄露

正确链路应该是：

text
前端
→ 学习者的后端 API
→ 后端读取安全保存的 API Key
→ 后端调用模型
→ 后端返回结果给前端

4.3 Server Deployment：后端服务部署

一个 AI App 后端可以部署在不同平台：

text
Vercel / Railway / Render / Fly.io
AWS / GCP / Azure
阿里云 / 腾讯云 / 火山云
自建服务器

但当前阶段无需研究每个平台细节。需要先知道：

text
前端部署 ≠ 后端部署 ≠ AI 服务部署 ≠ 数据库部署

常见结构：

text
用户浏览器
→ 前端 App
→ API Server
→ Database
→ LLM Provider
→ Logs / Monitoring

如果是复杂 AI 系统，还会多出：

text
Queue
Worker
Vector Database
Object Storage
Eval Pipeline
Observability Platform

4.4 Database Migration：数据库迁移

数据库结构会随产品演进而变化。

产品迭代时会发生：

text
新增用户字段
新增记忆表
新增 AI 调用日志表
新增工具调用表
修改消息结构
修改记录结构

数据库迁移就是：

用可追踪、可回滚的方式修改数据库结构。

学习者需要知道：

text
数据库结构不能靠开发手动乱改
每次变更应该有 migration 文件
线上数据库变更要谨慎

4.5 Queue / Async Jobs：队列与异步任务

部分任务适合进入异步队列，避免让用户同步等待。

例如：

text
上传检查报告 → OCR 识别
生成阶段总结
批量生成分享内容
定时回访
长期记忆抽取
跑评测任务
发通知

这些适合放进 Queue / Worker。

同步请求：

text
用户点一下
→ 后端立即处理
→ 用户等结果

异步任务：

text
用户提交任务
→ 后端先返回“已收到”
→ 队列慢慢处理
→ 处理完再通知 / 更新状态

需要形成的判断：

text
用户必须立刻看到的 → 同步
耗时、可延迟、可重试的 → 异步

4.6 Cache：缓存

缓存就是：

把经常用、短时间内不必重复计算的数据临时存起来。

AI 应用里可能缓存：

text
用户阶段信息
知识库检索结果
模型生成的摘要
高频配置
权限信息

但不能随便缓存所有东西。尤其涉及：

text
用户隐私
医疗敏感信息
记忆内容
临时风险状态

缓存要谨慎。

4.7 Rate Limit：限流

限流就是：

控制单位时间内可以请求多少次。

为什么重要？

text
防止恶意刷接口
防止成本失控
防止模型服务被打爆
防止第三方 API 限制导致系统崩

OpenAI 官方文档说明，rate limits 是 API 在特定时间内对访问次数或访问量的限制；生产应用必须理解和规划 rate limits。

学习者需要能问开发：

text
单用户每分钟最多多少次 AI 请求？
同一 IP 怎么限制？
高成本模型怎么限制？
重试有没有指数退避？
模型超限时怎么降级？

4.8 Monitoring / Alerting：监控与告警

监控回答：

text
系统现在是否正常？

告警回答：

text
出问题时谁会知道？

AI 应用至少要监控：

text
接口错误率
模型调用失败率
平均延迟
P95 / P99 延迟
Token 消耗
单用户成本
工具调用失败率
RAG 检索失败率
Memory 写入异常
Guardrails 触发率

4.9 Cost Control：成本控制

AI 应用成本需要同时关注服务器、模型调用和上下文规模。

还包括：

text
模型输入 token
模型输出 token
Embedding
图片识别
语音识别
向量数据库
日志存储
评测调用
重试调用

常见成本风险：

text
上下文塞太长
每轮都用最贵模型
重复生成
没有缓存
失败后无限重试
用户恶意刷接口
日志和 trace 无限制存储

需要能够判断：

text
是否所有任务都需要最强模型？
是否所有历史都要塞进上下文？
是否低价值任务可以用便宜模型？
是否高成本功能需要次数限制？

4.10 Rollback：回滚

AI 应用回滚范围不只包含代码，还要能回滚：

text
Prompt 版本
模型版本
RAG 知识库版本
Memory 写入策略
Tool 调用策略
Guardrails 规则
Harness 路由逻辑

普通软件回滚：

text
代码版本 A → 代码版本 B → 出问题 → 回到 A

AI 系统回滚更复杂：

text
Prompt 改了
模型换了
RAG chunk 改了
Memory 策略改了
输出变差
但代码没报错

所以需要知道：

text
AI 系统的“坏”不一定是 bug
也可能是输出质量下降、风险上升、成本变高、语气变差

5. 真实系统链路：一个 AI 请求上线后怎么跑？

text
用户打开 App
→ 登录态校验 Auth
→ 前端发送 /api/chat
→ 后端读取用户信息
→ 检查请求频率 Rate Limit
→ 读取数据库中的用户状态
→ Harness 判断任务类型
→ 组装 Context
→ 必要时检索 RAG / 读取 Memory / 调 Tool
→ 选择模型 Model Routing
→ 调用 LLM API
→ 记录 Trace / Logs
→ Guardrails 检查输出
→ 返回前端
→ 写入消息记录 / 记忆候选 / 工具结果
→ 异步任务进入 Queue
→ 监控成本、延迟、错误

这条链路就是学习者应当能看懂的上线级 AI App 链路。

6. 少量代码片段：只看结构

6.1 环境变量读取

ts
const apiKey = process.env.OPENAI_API_KEY

只需知道：

text
process.env = 从运行环境读取配置
OPENAI_API_KEY = 不应该写死在代码里

6.2 一个简化的 AI 接口

ts
app.post("/api/chat", async (req, res) => {
  const userId = req.user.id
  const message = req.body.message
  await checkRateLimit(userId)
  const userState = await db.userState.findUnique({ where: { userId } })
  const context = await buildContext({ userId, message, userState })
  const result = await callModel({
    model: "fast-model",
    context,
    message
  })
  await db.aiLog.create({
    data: {
      userId,
      model: "fast-model",
      latencyMs: result.latency,
      tokenUsed: result.tokens
    }
  })
  res.json({ answer: result.text })
})

无需记忆语法，只需要看懂结构：

text
接请求
→ 限流
→ 查用户状态
→ 组装上下文
→ 调模型
→ 写日志
→ 返回结果

7. 常见误区

误区正确判断
Demo 能跑就能上线Demo 只证明局部可行，不证明稳定、安全、成本可控
部署只是发布网站AI 应用还涉及 Key、安全、日志、评测、回滚
成本只看模型单价真正成本来自 token、重试、长上下文、评测、多模态、存储
线上问题都是代码 bugAI 应用可能是 Prompt、Context、Memory、RAG、模型路由问题
日志可有可无没日志就无法定位、复盘、评测、优化
API Key 可以放前端严重错误，核心 Key 不能暴露在浏览器或 App 客户端
