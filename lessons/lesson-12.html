第 12 课 · Week 3

Tool Calling / Function Calling / MCP：从语言输出到系统动作

理解模型如何通过工具协议触发外部能力，以及工具执行的权限和校验边界。

工具调用MCP权限

课程目标

理解模型如何通过工具协议触发外部能力，以及工具执行的权限和校验边界。

1. 本课问题域

没有工具调用时，模型只能生成文本。

它可以说：

text
“我建议你查一下天气。”
“我可以帮助学习者整理提醒。”
“你可以去看一下日历。”

但它不能真的：

text
查天气
建提醒
查数据库
调用 OCR
生成报告
搜索文件
创建日程
发通知

Tool Calling 要解决的是：

让模型通过受控接口调用外部能力。

2. Tool Calling 在知识树里的位置

text
用户输入
→ Harness 判断任务
→ 模型判断需要哪个工具
→ 系统检查工具权限
→ 系统执行工具
→ 工具结果返回模型
→ 模型基于结果继续生成
→ 输出给用户
→ 记录 tool call 日志

注意：

模型通常不直接执行工具。

模型只是提出调用请求，真正执行的是学习者的应用系统。

OpenAI 官方 function calling 文档把 tool calling 描述为多步流程：先把可调用工具发给模型，模型返回 tool call，然后应用侧执行代码，再把工具结果发回模型，最后模型生成最终回复。

3. Tool、Function、MCP 的区别

A. Function Calling

Function Calling 是一种机制：

text
告诉模型有哪些函数可以用
模型输出要调用哪个函数以及参数
学习者的代码执行函数

例如：

json
{
  "tool_name": "get_user_profile",
  "arguments": {
    "user_id": "123"
  }
}

B. Tool Calling

Tool 是更宽泛的说法。

工具可以是：

text
函数
数据库查询
搜索
文件读取
OCR
日历
邮件
支付
地图
MCP Server

OpenAI Agents SDK 也把 tools 解释为让 agents 能采取行动，例如获取数据、运行代码、调用外部 API，甚至使用电脑。

C. MCP

MCP 是 Model Context Protocol。

它的作用是标准化 AI 应用如何连接外部数据源和工具。

可以这样理解：

text
没有 MCP：
每接一个工具，都要单独写一套连接方式。
有 MCP：
工具以统一协议暴露，AI 应用按统一方式连接。

MCP 官方文档把它定义为连接 AI 应用与外部系统的开源标准，可连接数据源、工具和工作流。

4. 0 基础理解：Tool Calling 并非“模型有手了”

很多人误解：

text
模型会调用工具 = 模型真的在执行代码

实际更准确的是：

text
模型输出一张“调用申请单”
系统检查申请单
系统执行
系统把结果交回模型

所以权限控制永远在系统侧，不在模型侧。

5. Tool Calling 的标准链路

text
1. 开发者定义工具
2. 后端把工具描述发给模型
3. 用户提出需求
4. 模型判断是否需要工具
5. 模型返回工具名和参数
6. 后端校验权限和参数
7. 后端执行工具
8. 后端把工具结果发回模型
9. 模型生成用户可读回复
10. 系统记录日志

6. 一个最小工具定义

无需掌握编写细节，只要看懂结构。

ts
const tools = [
  {
    name: "getUserProfile",
    description: "获取用户的基础资料和当前阶段",
    parameters: {
      type: "object",
      properties: {
        userId: {
          type: "string",
          description: "用户 ID"
        }
      },
      required: ["userId"]
    }
  }
]

只需看懂：

text
name = 工具名字
description = 告诉模型这个工具干嘛
parameters = 模型调用这个工具时需要提供哪些参数
required = 哪些参数必须有

7. 工具执行不应该缺少边界控制

每个工具都需要权限和边界。

工具风险需要什么控制
查用户资料隐私只能查当前用户
写记忆误记 / 敏感需要 Memory Policy
发通知打扰用户需要频率控制
创建日程影响真实生活需要确认
生成报告内容质量需要结构校验
医疗建议高风险需要 Guardrails
删除数据不可逆需要二次确认

8. Tool Calling 和 RAG / Memory 的关系

三者经常一起出现。

例如用户问：

text
“帮我整理一下上次产检后要问医生的问题。”

系统可能需要：

text
1. 查数据库：上次产检记录
2. 查 Memory：用户长期担心的问题
3. 查 RAG：相关检查指标的基础知识
4. 调模型：生成问医生清单
5. 写工具结果：保存成一个清单

这里：

text
数据库查询 = Tool
记忆检索 = Memory
知识检索 = RAG
清单保存 = Tool
模型生成 = LLM
整体调度 = Harness

9. Tool Calling 的常见失败

text
1. 模型选错工具
2. 参数缺失或格式错误
3. 工具权限不该开放
4. 工具返回结果太长
5. 工具失败没有降级
6. 模型误以为工具结果已经展示给用户
7. 多工具调用顺序混乱
8. 没有记录 tool call 日志

所以 Tool Calling 一定要配合：

text
Tool Schema
Parameter Validation
Permission Check
Fallback
Tracing
Evals

10. MCP 什么时候重要

当前阶段不用急着实现 MCP，但要知道它的意义。

MCP 更适合：

text
1. 要接很多外部工具
2. 要让不同 AI 客户端复用同一套工具
3. 要接企业内部数据源
4. 要接文件、数据库、GitHub、浏览器、日历等系统
5. 要建立标准化工具生态

早期产品未必一开始就上 MCP，但它代表了工具连接的方向。

阶段复盘

这三课是 AI 应用从“会回答”走向“能使用信息、持续理解用户、调用外部能力”的关键。

三者边界

模块最短定义典型问题
RAG查外部知识“这个指标是什么意思？”
Memory记住个人状态“我之前说过我不喜欢什么？”
Tool调用外部能力“帮我查一下 / 保存一下 / 生成一下”

三者协作

text
用户输入
→ Harness 判断任务
→ 需要事实知识：走 RAG
→ 需要个人连续性：查 Memory
→ 需要执行动作：调用 Tool
→ 模型生成
→ Guardrails 检查
→ 输出给用户
→ 写日志 / 评测

学习者应当形成的判断

text
并非所有问题都查 RAG
并非所有历史都写 Memory
并非所有动作都交给模型
并非所有工具都能自动执行
Harness 必须在中间做控制
