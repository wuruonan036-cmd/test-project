第 14 课 · Week 3

Harness 工程：把模型纳入可控运行系统

系统理解 Harness 对输入、任务、风险、上下文、模型、工具、记忆、安全和日志的调度。

Harness控制层运行时

课程目标

系统理解 Harness 对输入、任务、风险、上下文、模型、工具、记忆、安全和日志的调度。

1. 知识树定位

Harness 位于整棵树的控制层。

它不等于：

text
模型
Prompt
RAG
Memory
Agent 框架
后端服务

它更像一个“运行控制系统”：

text
用户输入
→ Harness 判断
→ 选择上下文
→ 选择 Prompt
→ 选择模型
→ 是否调用 RAG
→ 是否读写 Memory
→ 是否调用 Tool
→ 是否触发 Guardrails
→ 是否写日志和评测样本
→ 返回结果

2. 先给定义

Harness 工程，就是把不稳定的大模型能力，包进一套可控、可追踪、可评测、可降级、可上线的工程控制层里。

更短：

text
Harness = AI 应用的运行控制层。

3. 为什么需要 Harness？

因为模型本身不负责产品稳定性。

模型只负责：

text
根据输入生成输出

但真实产品还需要负责：

text
这个请求是什么任务？
用户是谁？
当前状态是什么？
应该看哪些上下文？
该用哪个模型？
能不能调工具？
调什么工具？
能不能写记忆？
输出有没有风险？
失败了怎么办？
这次调用怎么记录？
下次如何评测？

这些能力需要 Harness 承担运行控制，不能依赖模型自动稳定完成。

4. Harness 控制什么？

4.1 输入解析 Input Parsing

把用户输入变成系统能理解的结构。

用户说：

text
“我这两天有点担心，昨天检查那个指标是否不太好？”

系统要解析：

text
情绪：担心
指代：昨天检查
任务：检查解释 + 情绪支持
需要：读取历史检查记录
风险：可能需要安全判断

4.2 任务分类 Task Classification

判断这次请求属于什么类型。

text
open_chat
check_report
risk_signal
doctor_questions
nutrition
recording
export
family_share

任务分类决定后续链路。

4.3 用户状态读取 User State Loading

读取必要状态，避免把所有数据直接塞入上下文。

text
用户阶段
孕周 / 产后天数
最近检查
未完成事项
关键偏好
最近风险事件

4.4 上下文组装 Context Assembly

把这次任务需要的信息组装成 Context Pack。

text
system instruction
task instruction
user state
relevant memory
retrieved knowledge
recent messages
tool results
output schema
safety rules

4.5 Prompt 选择 Prompt Selection

不同任务应使用不同模板，避免依赖万能 Prompt。

text
companion_chat_prompt
check_explain_prompt
risk_triage_prompt
doctor_question_prompt
memory_extract_prompt
family_share_prompt

4.6 模型路由 Model Routing

不同任务用不同模型。

text
轻量模型：分类、摘要、标题
高质量模型：复杂解释、陪伴主回复
推理模型：多步骤判断、复杂规划
多模态模型：图片 / 报告识别

4.7 工具权限 Tool Permission

工具调用需要权限边界，不能由模型自由决定。

Harness 要判断：

text
这个用户有没有权限？
这个任务是否允许调这个工具？
参数是否完整？
调用失败怎么办？
是否需要人工确认？

4.8 记忆策略 Memory Policy

决定是否读记忆、写记忆、禁止写记忆。

text
这次是否需要用户偏好？
这次是否需要历史事件？
这句话是否值得写入长期记忆？
这类敏感信息是否不能写？
用户是否关闭了某类记忆？

4.9 安全控制 Guardrails

Harness 要把安全检查放在多个节点：

text
输入后
任务分类后
工具调用前
模型输出后
产品动作前

4.10 失败降级 Fallback

模型失败、工具失败、RAG 失败、记忆失败时怎么办？

text
换模型
跳过工具
返回安全提示
提示用户补充信息
转人工
只保存记录不生成建议

4.11 日志与评测 Logging / Evals

每次 AI 调用都应该留下足迹：

text
用户输入
任务类型
调用模型
使用 Prompt 版本
使用上下文
RAG 检索结果
Memory 读写
Tool 调用
安全检查结果
输出结果
耗时
成本
错误

后面 Evals 和 Observability 会基于这些日志工作。

5. Harness 与其他模块的关系

模块它负责什么Harness 怎么用它
Prompt定义任务协议选择对应 Prompt 版本
Context提供本轮材料决定放哪些上下文
RAG检索外部知识决定是否检索、检索什么
Memory保存长期状态决定读、写、删、抑制
Tool执行动作决定是否允许调用
Model生成或判断决定用哪个模型
Guardrails安全检查决定检查节点和策略
Evals质量评测利用 Harness 日志回归测试

6. 真实系统链路：Harness 如何处理一次请求

用户输入：

text
“帮我整理一下今天去医院要问医生的问题。”

Harness 处理链路：

text
1. 输入解析
   - 用户想生成问医生清单
2. 任务分类
   - doctor_questions
3. 读取状态
   - 最近检查记录
   - 最近用户担忧
   - 当前阶段
   - 未完成事项
4. 上下文组装
   - 用户最近问题
   - 检查摘要
   - 相关记忆
   - 输出格式要求
5. Prompt 选择
   - doctor_question_prompt
6. 模型路由
   - 选择适合结构化生成的模型
7. 生成结构化结果
   - 问题清单
   - 优先级
   - 给医生的表达方式
8. 输出前检查
   - 是否有医疗越界
   - 是否暗示诊断
   - 是否需要建议及时就医
9. 返回前端
   - 展示清单
   - 可编辑
   - 可保存到空间
10. 写日志
   - 保存调用记录
   - 可进入后续评测

7. 少量代码片段：只看结构

ts
async function runHarness(input, userId) {
  const task = await classifyTask(input)
  const userState = await loadUserState(userId, task)
  const context = await buildContext({
    input,
    task,
    userState,
    includeMemory: shouldUseMemory(task),
    includeRag: shouldUseRag(task),
  })
  const model = selectModel(task)
  const prompt = selectPrompt(task)
  const result = await callModel({
    model,
    prompt,
    context,
  })
  const safeResult = await runGuardrails(result, task)
  await writeTrace({
    userId,
    task,
    model,
    promptVersion: prompt.version,
    contextSummary: context.summary,
    result: safeResult,
  })
  return safeResult
}

只需看懂这个结构：

text
Harness 不等同于一次模型调用
Harness 是模型调用前后的整套控制流程

8. Harness 和 Agent 框架的区别

对比HarnessAgent 框架
本质工程控制思想 / 控制层具体实现工具
关注点任务、上下文、模型、工具、安全、日志如何编排 Agent / Tool / State
是否必须用框架不一定可选
例子自己写的一套控制逻辑LangGraph / OpenAI Agents SDK / Pydantic AI

需要先理解 Harness 思想，再看框架。

9. 常见误区

误区正确理解
Harness 就是 Prompt 管理Prompt 只是其中一部分
Harness 就是 AgentAgent 是一种执行方式，Harness 是控制系统
Harness 必须用复杂框架小产品可以先用简单代码实现
记忆应该由模型自己决定记忆读写必须被系统控制
评测可以上线后再说没日志就无法评测，Harness 阶段就要留痕

10. 本课实战判断

后续评审 AI 后端方案时，先问：

text
1. 有没有任务分类？
2. 有没有上下文组装策略？
3. 有没有 Prompt 版本管理？
4. 有没有模型路由？
5. 有没有 RAG / Memory 的调用条件？
6. 有没有工具权限控制？
7. 有没有输出前安全检查？
8. 有没有失败降级？
9. 有没有 trace / 日志？
10. 有没有把失败案例转成 eval 的机制？

少了这些，只是“接了一个模型”。
