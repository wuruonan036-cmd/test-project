2. 先区分三个词

2.1 Logs

Logs 是日志。

它通常记录：

text
某个时间
某个用户
发生了某个事件
状态是什么
有没有错误

例子：

text
2026-05-19 10:32:01 user_123 called /api/chat model=gpt-xxx latency=2.4s

2.2 Trace

Trace 是一次完整请求或工作流的轨迹。

它回答：

text
这次 AI 请求从头到尾经历了哪些步骤？

例子：

text
用户输入
→ 任务分类
→ 读取记忆
→ RAG 检索
→ 调用模型
→ Output Guard
→ 返回用户

2.3 Span

Span 是 Trace 里的一个步骤。

比如：

text
一次模型调用是一个 span
一次工具调用是一个 span
一次 RAG 检索是一个 span
一次 guardrail 检查是一个 span

可以这样理解：

text
Trace = 一整条链路
Span = 链路里的每一个环节
Log = 每个环节或事件的记录

3. 为什么 AI 系统特别需要 Tracing？

普通后端出错，常见原因是：

text
代码 bug
数据库错误
网络错误
权限错误

AI 系统出错，还会多很多原因：

text
Prompt 不清楚
Context 塞错了
RAG 召回错了
Memory 注入错了
模型路由错了
工具参数错了
Guardrails 没拦住
模型随机漂移
输出格式不合规

因此不能只问：

text
模型为什么答错？

需要追问：

text
这一次请求到底经历了哪些步骤？
每一步输入是什么？
每一步输出是什么？
哪个节点开始偏了？

这就是 tracing 的价值。

4. 一次 AI 请求应该记录什么？

最小 trace 字段建议：

字段说明
trace_id一次完整请求的编号
user_id用户编号，注意隐私处理
session_id会话编号
timestamp时间
entry_point从哪个页面或入口发起
task_type任务类型
risk_level风险等级
model使用的模型
prompt_versionPrompt 版本
context_items注入了哪些上下文
memory_read读了哪些记忆
memory_write写了哪些记忆
rag_query检索 query
retrieved_docs检索到的知识片段
tool_calls调用了哪些工具
guardrail_results安全检查结果
output_type文本 / JSON / 工具结果
latency延迟
cost成本
error错误
user_feedback用户反馈

5. Tracing 帮助学习者回答什么问题？

问题 1：为什么这次答错？

Trace 可以用于观察：

text
是否任务分类错了？
是否上下文没带？
是否 RAG 召回错了？
是否模型路由到了便宜模型？
是否 Output Guard 没拦住？

问题 2：为什么成本变高？

Trace 可以看到：

text
是否上下文太长？
是否调用了太贵的模型？
是否重复调用工具？
是否一个请求触发多次模型调用？

问题 3：为什么延迟变慢？

Trace 可以看到：

text
是模型慢？
是 RAG 检索慢？
是工具慢？
是数据库慢？
是 guardrails 慢？

问题 4：为什么用户不满意？

Trace 可以结合用户反馈看：

text
用户踩了差评
→ 找到 trace
→ 看模型看到了什么
→ 看输出怎么生成
→ 把这个案例加入 eval dataset

6. 少量代码：看懂 trace 的结构

ts
const trace = {
  trace_id: "trace_001",
  user_id: "user_123",
  task_type: "medical_question",
  risk_level: "medium",
  model: "reasoning-model",
  prompt_version: "v3.2",
  spans: [
    {
      name: "task_classification",
      latency_ms: 180,
      output: { task_type: "medical_question" }
    },
    {
      name: "memory_read",
      latency_ms: 90,
      output: { memories_used: 2 }
    },
    {
      name: "rag_retrieval",
      latency_ms: 320,
      output: { docs_found: 4 }
    },
    {
      name: "model_call",
      latency_ms: 2400,
      output_type: "structured_json"
    },
    {
      name: "output_guardrail",
      latency_ms: 160,
      output: { safe: true }
    }
  ],
  total_latency_ms: 3150
}

只需看懂：

text
trace_id = 这次完整请求
spans = 每个步骤
latency_ms = 每一步耗时
output = 每一步结果

7. Observability 和普通 Logs 的区别

Logs 只说明发生了什么。

Observability 要用于理解系统为什么这样表现。

能力只做 Logs做 Observability
查错误可以可以
看完整链路不一定可以
分析成本很弱可以
分析延迟很弱可以
复盘 AI 行为很弱可以
连接 Evals很弱可以
找到失败根因很难更可行

8. AI 产品最小可观测系统

第一版不需要很复杂，但至少要有：

text
1. 每次模型调用日志
2. 每次工具调用日志
3. 每次 RAG 检索日志
4. 每次 Memory 读写日志
5. 每次 Guardrails 结果
6. 每次用户反馈
7. 每次错误和降级
8. 成本与延迟统计

没有这些，后续无法优化。

9. Tracing、Evals、Harness 的关系

三者关系是：

text
Harness 控制流程
Tracing 记录流程
Evals 评价流程

更完整：

text
Harness 决定这次怎么跑
→ Tracing 记录这次实际怎么跑
→ Evals 判断这次跑得好不好
→ 失败案例反哺 Harness / Prompt / Context / Model / Tool

这是 AI 应用工程的核心闭环。

text
