第 08 课 · Week 2

Structured Output：可被程序使用的结构化结果

理解结构化输出如何把模型结果接入确定性软件流程。

JSONSchema校验

课程目标

理解结构化输出如何把模型结果接入确定性软件流程。

1. 课程目标

学完这一课，需要能回答：

text
1. 什么是 Structured Output？
2. 为什么 AI 产品不能只返回自然语言？
3. JSON、Schema、字段、枚举分别是什么？
4. Structured Output 和 Tool Calling、Workflow、Evals 有什么关系？
5. 为什么它是 Harness 工程的基础能力？

2. 定义

Structured Output 就是让模型按照预设结构输出结果。

反例：

text
这份报告看起来没什么大问题，但有些指标建议下次问医生。

核心是这样：

json
{
  "summary": "整体未发现明显高风险信号，但有 2 个指标建议复查时向医生确认。",
  "risk_level": "medium",
  "key_points": [
    "指标 A 略高",
    "指标 B 需要结合孕周判断"
  ],
  "doctor_questions": [
    "这个指标是否需要复查？",
    "是否和当前孕周有关？"
  ],
  "should_create_record": true
}

前者适合人读。 后者适合产品系统继续处理。

3. 为什么真实产品需要结构化输出？

产品后端除自然语言文本外，还需要触发可执行动作。

例如模型输出后，系统可能要判断：

text
要不要生成一张卡片？
要不要写入空间记录？
要不要触发回访？
要不要提醒用户问医生？
要不要进入风险流程？
要不要调用另一个工具？
要不要进入评测样本？

自然语言很难让程序稳定判断。 结构化输出可以。

4. 基础概念：JSON 是什么？

JSON 可以理解成一种标准数据格式。

json
{
  "name": "小橙",
  "age": 1,
  "is_active": true,
  "tags": ["AI", "陪伴"]
}

只需知道：

text
字符串：用引号包起来，例如 "summary"
数字：例如 1、20、3.5
布尔值：true / false
数组：用 []，表示一组东西
对象：用 {}，表示一组字段

5. Schema 是什么？

Schema 是结构规则。

如果 JSON 是“结果”，Schema 就是“结果必须长什么样”。

例如规定：

text
risk_level 只能是 low / medium / high
should_create_record 只能是 true / false
doctor_questions 必须是一个列表
summary 必须是一句话

这就是 Schema 的作用。

6. 为什么枚举 enum 很重要？

枚举就是限定可选值。

比如风险等级不能让模型随便写：

text
有点危险
还行
不太妙
可能要小心
中等偏高

后端程序无法稳定判断。

所以要规定：

text
risk_level = low / medium / high / emergency

这样程序才能处理：

text
low → 正常回复
medium → 建议问医生
high → 明确建议尽快咨询医生
emergency → 触发紧急安全流程

7. Structured Output 在请求链路里的位置

text
用户输入
→ Harness 判断任务
→ 选择 Prompt
→ 组装 Context
→ 调模型
→ 模型返回 Structured Output
→ 后端解析字段
→ 决定产品动作
→ 返回前端 / 写数据库 / 触发工具

关键点：

text
Structured Output 是模型输出和产品动作之间的桥。

8. 少量代码：只看结构

ts
const schema = {
  type: "object",
  properties: {
    summary: { type: "string" },
    risk_level: { 
      type: "string", 
      enum: ["low", "medium", "high"] 
    },
    should_create_record: { type: "boolean" },
    doctor_questions: {
      type: "array",
      items: { type: "string" }
    }
  },
  required: ["summary", "risk_level", "should_create_record"]
};

只需看懂：

text
summary 是字符串
risk_level 只能从 low / medium / high 里选
should_create_record 是 true 或 false
doctor_questions 是字符串列表
required 表示必须有这些字段

9. 产品里常见的结构化输出类型

9.1 任务分类

json
{
  "task_type": "report_explanation",
  "confidence": 0.87
}

用途：让 Harness 知道下一步走哪个流程。

9.2 风险分类

json
{
  "risk_level": "medium",
  "risk_reasons": ["用户描述了持续不适", "信息不足，需要医生确认"]
}

用途：决定是否触发 Guardrails。

9.3 内容卡片生成

json
{
  "card_type": "doctor_question_list",
  "title": "下次产检可以问医生的 3 个问题",
  "items": [
    "这个指标是否需要复查？",
    "是否和当前孕周有关？",
    "饮食或作息上需要注意什么？"
  ]
}

用途：前端可以直接渲染成卡片。

9.4 记忆写入判断

json
{
  "should_write_memory": true,
  "memory_type": "preference",
  "memory_text": "用户希望回答更直接，不要过度安慰。"
}

用途：决定是否写入长期记忆。

9.5 工具调用前判断

json
{
  "should_call_tool": true,
  "tool_name": "search_medical_knowledge",
  "query": "孕中期 胎动 减少 需要注意什么"
}

用途：让系统判断是否进入工具调用。

10. Structured Output 和 Tool Calling 的关系

二者都和“结构”有关，但不一样。

概念作用
Structured Output让模型输出固定结构，供系统继续处理
Tool Calling让模型请求调用某个工具，并传入结构化参数

简单说：

text
Structured Output = 输出结果结构化
Tool Calling = 动作请求结构化

11. Structured Output 和 Evals 的关系

结构化输出也让评测更容易。

如果模型只输出自然语言，很难稳定评测：

text
它有没有识别风险？
它有没有生成医生问题？
它有没有建议写入记录？

如果输出是 JSON，就可以直接检查：

text
risk_level 是否正确
doctor_questions 是否为空
should_create_record 是否符合预期
memory_type 是否越界

这就是为什么 Structured Output 是 Evals 的基础之一。

12. 实战判断：什么时候必须结构化？

这些场景必须结构化：

text
1. 任务分类
2. 风险等级判断
3. 是否写入记忆
4. 是否生成卡片
5. 是否调用工具
6. 是否触发回访
7. 是否进入人工审核
8. 生成列表、表格、清单
9. 进入评测系统

这些场景可以自然语言：

text
1. 用户直接看的一段解释
2. 情绪陪伴回复
3. 开放式聊天
4. 总结后的自然表达

真实产品通常是：

text
模型同时输出：
1. 给用户看的自然语言
2. 给系统看的结构化字段
